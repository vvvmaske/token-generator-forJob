# Генератор задач

Минимальный асинхронный сервис на FastAPI и PostgreSQL. Модель и цепочки провайдеров создаются миграцией. В каждом из четырёх API-процессов работает сторож; блокировка `FOR UPDATE SKIP LOCKED` распределяет просроченные попытки между процессами.

## Запуск

Нужны Docker и Docker Compose. В корне проекта:

```sh
docker compose up --build
```

Сервис доступен на `http://localhost:8000`. При старте контейнер API применяет миграции до запуска четырёх Uvicorn workers. Для локального запуска после установки пакетов: `alembic upgrade head`, затем `uvicorn app.main:app --workers 4`.

Миграции: `alembic upgrade head`; новую создайте командой `alembic revision -m "описание изменения"`, внесите SQL в созданный файл и примените `alembic upgrade head`.

Пользователь начинает с нулевым балансом; отправьте подписанный вебхук оплаты. Подпись — HMAC-SHA256 точных байтов JSON в `X-Signature`, секрет `WEBHOOK_SECRET` (в Compose демонстрационный `dev-secret-change-me`). Пример generate: `{"user_id":"u1","model_slug":"image-fast","prompt":"cat","ref_images":[]}`.

## Надёжность денег и задач

Каждое зачисление/списание/возврат записывается в `ledger` в той же транзакции, что меняет баланс. Уникальность `(reason, reference)` не даёт второй раз провести одно начисление или возврат. Платёж имеет уникальный `payment_id`; задача блокируется `FOR UPDATE` на обработке результата, а попытка переводится из `waiting` только один раз. Повторный и параллельный вебхук поэтому становится безопасным no-op.

Если процесс падает во время вебхука, незавершённая транзакция PostgreSQL откатывается, провайдер может повторить вебхук. Если попытка уже подтверждена в базе, повторный вебхук игнорируется. Вызов провайдера выполняется вне DB-транзакции; сбой процесса в коротком промежутке отправки может оставить попытку `sending`. В этой учебной реализации watchdog обрабатывает только `waiting`, поэтому для боевого применения стоит добавить lease/recovery для `sending`.

### Поздний completed

После watchdog попытка считается исчерпанной. Если другая нога ещё выполняется, поздний результат первой ноги игнорируется. Если все ноги исчерпаны и токены уже возвращены, задача остаётся `failed`, поздний результат тоже игнорируется. Так не выдаём результат одновременно с возвратом. Это политика «возврат окончателен»; она безопасна для баланса, но может потерять полезный результат, и провайдерский файл остаётся невостребованным.

## Настройки fake provider

`FAKE_ALPHA_ERROR` / `FAKE_BETA_ERROR`: `technical`, `moderation` или `payload` на вебхуке; `FAKE_ALPHA_SYNC=503` имитирует синхронный отказ; `FAKE_SILENT=1` отключает вебхук; `FAKE_DUPLICATE=1` посылает повтор; `FAKE_DELAY` меняет задержку. Для тестов fake понимает маркеры в prompt: `[fail:alpha:technical]`, `[fail:beta:moderation]`, `[silent:alpha]` и соответствующие варианты.

## Тесты

Поднять сервис командой выше. В отдельном PowerShell установить зависимости `pip install -e ".[test,migrate]"` и запустить `pytest -q`. Тесты подключаются к опубликованному порту PostgreSQL `localhost:5432` и API `localhost:8000`; они проверяют 20 повторных оплат, отказ первой ноги с переходом ко второй, 10 повторных отказов последней ноги и поздний результат после сторожа.
